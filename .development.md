
# Development Guide

This document explains how native.cr works internally for contributors.

## Architecture Overview

native.cr is a cross-platform mobile framework that compiles Crystal code directly to ARM64 binaries for Android and iOS. No JavaScript bridge. No interpreter. Just Crystal talking to native APIs through FFI.

```

┌─────────────────────────────────────────────────────────────┐
│  User's Crystal App (src/main.cr)                          │
├─────────────────────────────────────────────────────────────┤
│  native.cr Framework (src/native/framework/.cr)           │
│  - UI components, animations, gestures, camera, etc.       │
├─────────────────────────────────────────────────────────────┤
│  Core Modules (src/native/core/.cr)                       │
│  - State preservation, process management                  │
├─────────────────────────────────────────────────────────────┤
│  Platform Engines (src/native/engine/*.cr)                 │
│  - Android: C + JNI bridge                                 │
│  - iOS: Objective-C + Metal bridge                         │
├─────────────────────────────────────────────────────────────┤
│  Device OS (Android/iOS)                                   │
└─────────────────────────────────────────────────────────────┘

```

## Directory Structure

```

src/native/
├── core/              # Core runtime (state, process)
├── framework/         # User-facing APIs (UI, camera, etc.)
├── engine/            # Platform engines
│   ├── android/       # C engine + JNI for Android
│   └── ios/           # Objective-C engine for iOS
├── cli/               # Command line tools (build, doctor, reload)
└── native.cr          # Main entry point

spec/                  # Test suite
cli/                   # Shell scripts (create project)
assets/                # Logos, branding

```

## How It Works

### 1. Compilation Flow

When a developer runs `native.cr build android`:

1. CLI passes `-D android` and `--target aarch64-linux-android` to Crystal
2. Crystal compiler reads `src/native.cr`
3. Conditional compilation includes only Android-specific code
4. Framework files use `{{ if flag?(:android) }}` to include JNI calls
5. Output is `libnative_cr.so` (shared library)

When the same developer runs `native.cr build ios`:

1. CLI passes `-D ios` and `--target aarch64-apple-ios`
2. Same Crystal code, but iOS branches are compiled
3. Output is `NativeCr.framework` (static library)

### 2. State Preservation (Fast Restart)

React Native has hot reload. Crystal cannot do that because code is compiled to native.

My solution: fast restart with state preservation.

```

1. File watcher detects change
2. Signal USR1 sent to running app
3. App serializes @[Preserve] properties to JSON
4. Old process terminates
5. Crystal recompiles changed files
6. New process starts
7. JSON state loaded back into @[Preserve] properties

```

Total time: ~300ms. Not hot reload, but good enough.

### 3. Platform Bridge Architecture

**Android:**

```

Crystal Code → JNI Bindings (crystal.cr) → C Engine → NDK → Android

```

The C engine (`android/native.c`):
- Creates OpenGL ES context
- Handles `android_main` entry point
- Forwards touch events to Crystal
- Calls Crystal's `crystal_android_main` export

**iOS:**

```

Crystal Code → Obj-C Bridge → Metal Renderer → iOS

```

The Objective-C bridge:
- Creates UIApplication and UIViewController
- Sets up CAMetalLayer for rendering
- Forwards CADisplayLink callbacks to Crystal
- Calls Crystal's `ios_render_frame` export

### 4. Framework Module Loading

`src/native.cr` loads everything with wildcards:

```crystal
require "./native/core/*"
require "./native/framework/*"
require "./native/cli/*"
```

This automatically includes all .cr files in those directories.

Platform engines are conditionally loaded:

```crystal
{% if flag?(:android) %}
  require "./native/engine/android/*"
{% elsif flag?(:ios) %}
  require "./native/engine/ios/*"
{% end %}
```

## Adding a New Feature

### Adding a New UI Component

1. Create src/native/framework/my_component.cr
2. Inherit from UI::View or UI::Text etc.
3. Implement draw(renderer) method
4. Add platform-specific drawing in {{ if flag?(:android) }} blocks

Example:

```crystal
class MyComponent < UI::View
  def draw(renderer)
    {{ if flag?(:android) }}
      LibAndroid.draw_my_component(renderer, x, y, width, height)
    {{ elsif flag?(:ios) }}
      LibIOS.draw_my_component(renderer, x, y, width, height)
    {{ end }}
  end
end
```

### Adding a New Platform API

1. Add C/Obj-C function in engine layer
2. Add Crystal binding in engine/android/bridge.cr or engine/ios/bridge.cr
3. Add Crystal wrapper in framework/my_api.cr
4. Use conditional compilation to call correct platform

### Adding a New CLI Command

1. Create src/native/cli/my_command.cr
2. Implement run method
3. Add case in src/native.cr to route command

## Testing

Run all tests:

```bash
make test
```

Run specific test:

```bash
crystal spec spec/framework_spec.cr
```

Building Locally

```bash
# Build CLI tool
make build

# Run locally
./.build/native.cr doctor

# Install globally
make install
```

## Common Gotchas

| Issue | Solution |
| ----- | ----- |
| flag?(:android) returns | false Pass -D android during compilation | 
| iOS Metal shaders not found | Compile .metal files with xcrun metal |
| Android JNI crashes | Ensure GC.init is called before any Crystal code | 
| State not preserving Add | @[Preserve] annotation to properties | 
| Fast restart not working |  Run native.cr reload, not crystal run |
